# 워커 H — 가이드·자리표시자 마커를 hwpx에서 빨간색으로 출력

작업 디렉토리 `C:/Users/EKR/orca/ggthesis`.

## 목적

학위논문 hwpx에서 **본문이 아닌 것**(아직 못 채운 자리, 확정해야 할 결정, 검증해야 할 근거)을
지도교수·심사위원이 한눈에 구분하도록 **빨간 글자**로 출력한다.
사용자 요청 원문은 "논문에서 확인이 필요한 부분, 본 내용이 아닌 가이드·방향 등을 기재한 것은 빨간색으로 표시해줘"이다.

MD 원고는 단일 원본이므로 **고치지 않는다.** 색은 조립 단계에서 입힌다.
그래야 다음에 다시 조립해도 빨간색이 자동으로 따라온다.

## 배경 — 이관 파이프라인

`tools/hwpx_transfer/`가 MD 원고를 학위논문 hwpx로 조립한다.

```
논문구조/*.md  →  md_to_blocks.py  →  staging/*.blocks.json  →  blocks_to_hwpx.py  →  hwpx
```

계획서는 `plan/2026-07-25_MD원고_hwpx이관_오케스트레이션.md`다.
현재 최신 산출물은 `00. hwpx/260824_1826_경기공학_건축안전_윤혁_논문작성_작성본.hwpx`이며 136쪽·표 46개다.

**이 작업의 수정 대상은 `tools/hwpx_transfer/blocks_to_hwpx.py` 한 파일이다.**

## 빨간색으로 칠할 것 — 접두사로 판정한다 (총 615개)

대괄호로 시작하는 다음 5종이다. **여는 대괄호부터 닫는 대괄호까지 통째로** 빨갛게 한다.

| 접두사 | 개수 | 예 |
|---|---:|---|
| `[DATA PENDING` | 546 | `[DATA PENDING: 총 배포 부수]`, `[DATA PENDING]` |
| `[확정 필요` | 41 | `[확정 필요: 탐색적 요인분석 포함 여부]`, `[확정 필요]` |
| `[CITE_TODO` | 21 | `[CITE_TODO: 연도]` |
| `[그림 삽입 예정` | 6 | `[그림 삽입 예정: 고용노동부(2024) …]` |
| `[UNVERIFIED` | 1 | `[UNVERIFIED — Green(1991)의 서지 존재는 …]` |

`[확정 필요 — 교수님 협의]`처럼 콜론 대신 줄표를 쓰는 변형이 있으므로
**콜론을 요구하지 말고 접두사만으로 판정하라.**

## 빨간색으로 칠하면 안 되는 것 — 본문이다

대괄호라고 다 마커가 아니다. 아래는 **실제 논문 내용**이므로 검은색을 유지해야 한다.

- `[38, 41, 44]`, `[05, 42]`, `[04, 08, 23]` 등 — 04장 설문 문항표의 **근거 문헌 참조번호**다. 약 25개.
- `[0.974, 0.991]`, `[0.618, 0.848]` 등 — 03장의 **신뢰구간 수치**다. 5개.
- `[양식 1: 도입 현장용]`, `[양식 2: 미도입 현장용]` — 부록1의 **설문 양식 구분 라벨**이다. 2개.

**"대괄호 전부 빨강"으로 구현하면 오답이다.** 반드시 위 5종 접두사로만 판정하라.

## 적용 범위 — 본문 문단과 표 셀 둘 다

마커의 대부분(553개)이 **05장 표 안**에 있다. 표 셀을 빠뜨리면 작업의 의미가 없다.

`blocks_to_hwpx.py`에서 run을 만드는 지점은 다음 세 곳이다(행 번호는 대략이며 직접 확인하라).

- `Document.text_para()` 122~124행 — 단일 run 문단
- `Document.runs_para()` 131~135행 — bold 등 여러 run을 가진 문단
- `Document.cell_paragraphs()` 162~172행 — **표 셀** 문단

세 경로 모두에서, run 텍스트를 마커 경계로 쪼개고 마커 조각에만 빨간 `charPrIDRef`를 물려라.
마커 앞뒤의 일반 텍스트는 원래 `charPrIDRef`를 그대로 유지해야 한다.
한 run 안에 마커가 여러 개 있을 수 있고, 마커가 텍스트 중간에 올 수도 있다.

## 빨간 charPr 확보 — 여기가 핵심 함정이다

`write_hwpx()`(479~494행)는 `replacements`에 없는 ZIP 엔트리를 **양식에서 그대로 복사**한다.
현재 교체 대상은 `Contents/section1.xml`과 `Contents/section2.xml` 둘뿐이므로
`Contents/header.xml`은 양식 것이 그대로 나간다.

조사 결과 양식 `header.xml`에는 `charPr`가 134개(id 0~133) 있고,
그중 **`textColor="#FF0000"`인 것이 5개**다(id 15 포함).

두 가지 길이 있다. **판단은 네가 하되 근거를 보고하라.**

1. 기존 빨간 charPr를 재사용한다 — 단, 그 charPr의 **글꼴·크기·굵기가 본문/표 셀 charPr와 같아야 한다.**
   다르면 빨간 글자만 크기나 서체가 튀어 문서가 지저분해진다. 반드시 속성을 실측 대조하라.
2. 본문 charPr·표 셀 charPr를 각각 복제하고 `textColor`만 `#FF0000`으로 바꾼 새 charPr를 추가한다.
   이 경우 `header.xml`을 수정해 `itemCnt`(또는 그에 해당하는 개수 속성)를 함께 갱신하고,
   **`write_hwpx()`의 `replacements`에 `Contents/header.xml`을 추가**해야 반영된다.

본문과 표 셀의 charPr는 `staging/style_map.json`에 정의돼 있다.
bold 본문은 `BODY_BOLD_CHAR` 상수를 쓰므로 **볼드 문단 안의 마커**도 빠뜨리지 마라.

## 검증 — 직접 실행하고 실제 출력을 보고에 붙여라

**출력은 반드시 `tools/hwpx_transfer/staging/test_out/` 아래로 내라.**
`00. hwpx/`에는 쓰지 마라(아래 금지사항 참조).

```bash
cd "C:/Users/EKR/orca/ggthesis"
PYTHONIOENCODING=utf-8 PYTHONUTF8=1 python tools/hwpx_transfer/blocks_to_hwpx.py \
  --template "공학대학원_건축안전_윤혁_중소규모 건설현장을 위한 YOLO-VLM 안전관제 시스템 실증 연구 알람 피로도 완화와 안전 자원 제약성의 조절효과를 중심으로 - 복사본.hwpx" \
  --style-map tools/hwpx_transfer/staging/style_map.json \
  --blocks tools/hwpx_transfer/staging/ch01.blocks.json tools/hwpx_transfer/staging/ch02.blocks.json tools/hwpx_transfer/staging/ch03.blocks.json tools/hwpx_transfer/staging/ch04.blocks.json tools/hwpx_transfer/staging/ch05.blocks.json tools/hwpx_transfer/staging/ch06.blocks.json tools/hwpx_transfer/staging/apx1.blocks.json tools/hwpx_transfer/staging/apx2.blocks.json \
  --references tools/hwpx_transfer/staging/references.json \
  --output tools/hwpx_transfer/staging/test_out/red_marker_test.hwpx \
  --report tools/hwpx_transfer/staging/test_out/red_marker_report.md
```

UTF-8 점검 스크립트를 만들어 다음을 확인하고 실제 수치를 보고에 붙여라.

1. 빨간 charPrIDRef를 쓰는 run 개수가 **615개**다(위 표의 합계와 일치).
2. 마커 5종이 **모두** 빨간 run 안에 있다(종류별 개수도 표와 일치).
3. `[38, 41, 44]`·`[0.974, 0.991]`·`[양식 1`·`[양식 2`가 **빨간 run에 들어가지 않았다**.
4. 본문 총 문단 수가 이전 조립분과 같다(현재 668). 텍스트 유실이 없어야 한다.
5. 마커를 뺀 본문 텍스트가 이전 산출물과 동일하다(색만 바뀌고 글자는 그대로여야 한다).

**콘솔이 cp949라 한글이 깨진다.** 점검은 `python -c` 인라인 대신 UTF-8 `.py` 파일로 저장해 실행하고,
결과도 파일로 써서 읽어라. 그러지 않으면 한글 대조가 전부 거짓 음성이 된다.

## 행동 범위 — 다음은 하지 마라

이 워커의 범위는 좁다. 오케스트레이터의 권한을 상속하지 않는다.

- **`git add`·`git commit`·`git push`·`git checkout`·`git reset` 등 모든 git 명령 금지.**
  이전 라운드에서 워커가 이 금지를 어겨 무단 커밋 5건이 발생했다. 반복하지 마라.
  파일을 수정한 상태로 두고 보고만 하라. 커밋은 오케스트레이터가 한다.
- **`00. hwpx/` 아래에 쓰지 마라.** 최종 hwpx 조립과 표지 치환은 오케스트레이터가 단독·순차로 한다.
  네 출력은 `staging/test_out/`까지다.
- **`mcp__hwpx__` 쓰기 도구 금지.**
- **`논문구조/` 아래 MD 원고 수정 금지.** MD가 단일 원본이다. 색은 조립기가 입힌다.
- `MEMORY.md`, `CLAUDE.md`, `docs/*.md`, `plan/*.md` 수정 금지.
- 수정 허용 범위는 `tools/hwpx_transfer/blocks_to_hwpx.py`다.
  `staging/` 아래 산출물은 스크립트 실행으로 갱신되는 것이 정상이다.

하고 싶어지는 것이 생기면 멈추고, 무엇을 하려 했는지 최종 보고에 적어라. 판단은 오케스트레이터가 한다.

## 보고 형식

`worker_done`의 body에 다음을 담아라.

1. 빨간 charPr를 어떻게 확보했는지 — 재사용인지 신규 추가인지, 글꼴·크기 대조 근거
2. 세 run 생성 경로(본문 단일·본문 다중·표 셀)에 각각 어떻게 적용했는지
3. 검증 1~5의 실제 수치
4. 제외 대상(참조번호·신뢰구간·양식 라벨)이 검은색으로 남았다는 증거
5. `header.xml`을 건드렸다면 그 사실과 `write_hwpx` 변경 내용
