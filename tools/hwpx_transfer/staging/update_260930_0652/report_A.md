## 2. 명세 규약(메인 적용 시 필독)

1. **모든 idx는 base 덤프 원본 idx이다.** 한 문단에 대한 치환과 그 문단을 앵커로 삼는 삽입(예: 19·301·303·486·490·730)은 서로 다른 바이트 범위를 다루므로 함께 적용된다. 앵커는 삭제 대상과 겹치지 않는다.
2. **order는 해당 장 `new_blocks.json`의 블록 순번이다.** 제목 앞뒤 빈 줄은 제목 순번 ±0.5를 쓴다(예: 83.5 빈 줄 → 84 제2항 제목 → 84.5 빈 줄). 같은 `(anchor, position)` 큐 안에서 C 표와 섞여 정렬된다.

## 5. 검증 증거(`A_build.py` 1회 실행, `VALIDATION PASS`)

1. **유일 위치**: replace·delete·remove_object 대상 키 103개 중 중복 0건. `(anchor, position, order)` 중복 0건, C 표 order와의 충돌 0건.
2. **old 일치·적격성**: 모든 replace·delete의 `old`가 base 텍스트와 정확히 같다. 모두 `top_level`·`table_idx=null`·비표앵커·비그림 문단이다. remove_object 2건은 pic 컨트롤을 가진 최상위 문단이다. 삽입 앵커는 삭제 대상이 아니고, 템플릿은 모두 단일 run 최상위 문단이다.
3. **3자 대조**: 치환·삭제 대상 87건 모두 `HWPX == 옛 MD`이고, 치환 59건 모두 `새 MD ≠ 현재 HWPX`이다.
4. **변경 누락·삽입 순서(적용 시뮬레이션)**: base에 명세와 C 표 규약을 적용한 결과를 새 MD 블록 순서와 전수 대조했다. 제1장 19항목, 제2장 93항목, 제3장 91항목에서 불일치는 0건이다. 표 위치는 `TABLE:<표 N-M>` 순서까지 포함해 대조했다. 절·항 제목 3·18·18개는 모두 앞뒤가 빈 문단이며, 빈 줄이 연달아 두 개 나오는 곳은 0곳이다. 보존 그림은 40·449·496·510·551이다. 제4장 그림 1개는 범위 밖이며, 코디네이터가 말한 총 6개와 일치한다.
5. **coverage 전수**: 새 블록 216건이 모두 unchanged·replace·insert·C 표·그림 보존·사용자 수정 보존 중 하나로 분류되었다. 옛 최상위 문단 가운데 미처분 비공백 문단은 0건이다.
6. **메인 적용기 호환 드라이런(읽기 전용)**: `apply_update.py`와 같은 `surgical_ops`로 base.hwpx를 읽어 140개 연산을 확인했다. `S.own()==old` 59+42건, 삭제 문단 `_plain` 42건, remove_object 부모 검사 2건, 삽입 템플릿 `edit_paragraph(new=True)` 37건이 모두 통과했다. 패키지는 쓰지 않았고 SHA256은 불변이다.
