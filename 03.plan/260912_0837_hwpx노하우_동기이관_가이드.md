## 1. 이 방식의 핵심 아이디어

1. **MD가 단일 원본, hwpx는 사본이다.** 원고는 `01.docs/*.md`에 장별로 쓴다. 내용 수정은 항상 MD 먼저, 그다음 hwpx에 반영한다. hwpx를 직접 고치고 MD를 안 고치면 두 벌이 어긋나 심사 직전에 터진다.
2. **hwpx 반영은 두 경로뿐이다.**
   - **전체 조립** (`tools/hwpx_transfer/` 파이프라인): MD 전체 → 블록 JSON → 양식 hwpx 서식을 입혀 새 hwpx 생성. **처음 한 번**, 또는 구조를 갈아엎을 때만 쓴다.
   - **타깃 치환** (`fill_hwpx.py replace` + `verify_replace.py`): 문단 몇 개를 바꾸는 일상 작업. 바뀐 ZIP 엔트리만 다시 쓰고 나머지는 바이트 그대로 둔다.
   - 한글에서 직접 손본 내용이 hwpx에 쌓이기 시작하면 **전체 조립은 그 수정을 지운다.** 그래서 운영 단계에서는 타깃 치환만 쓴다.
3. **hwpx 산출물은 한글이 실제로 열어야 완료다.** ZIP·XML 검증을 다 통과한 파일이 한글에서 `Open=False`였던 사고가 있었다(2026-09-11). 검증 마지막 단계는 언제나 한컴 COM 개방 시험이다.
4. **파일명에 시각을 박고 원본은 절대 덮어쓰지 않는다.** `00. hwpx/YYMMDD_HHMM_논문명.hwpx`. 접두사가 가장 큰 파일이 최신본이다. 문서에 특정 파일명을 적어 두지 않는다(금방 낡는다).
5. **미완성 지점은 빨간 글자로 뽑는다.** `[DATA PENDING`, `[확정 필요`, `[CITE_TODO`, `[그림 삽입 예정`, `[UNVERIFIED` 접두사가 붙은 대괄호 구간은 조립 단계에서 빨간 `charPr`를 입힌다. 지도교수·심사위원이 빈 자리를 한눈에 본다. 색 정보는 MD가 아니라 조립기(`blocks_to_hwpx.py`)가 갖는다.

## 4. C. 노하우 — 작업 흐름

### 4-1. 처음 한 번: MD → hwpx 전체 조립

```bash
# 저장소 루트에서
PYTHONIOENCODING=utf-8 python tools/hwpx_transfer/md_to_blocks.py
PYTHONIOENCODING=utf-8 python tools/hwpx_transfer/blocks_to_hwpx.py \
  --template "<학교 양식 hwpx>" \
  --style-map tools/hwpx_transfer/staging/style_map.json \
  --blocks tools/hwpx_transfer/staging/ch01.blocks.json ... \
  --references tools/hwpx_transfer/staging/references.json \
  --output "00. hwpx/YYMMDD_HHMM_논문명.hwpx"
```

`--smoke`를 주면 `--output` 없이 `staging/test_out/smoke.hwpx`로 시험만 한다. 조립 후 `extract_text.py --verify-blocks`로 누락 0건, `verify-hwpx.ps1`로 `Open=True`, `render-pdf.ps1`로 표 쪽 육안 확인까지 해야 완료다.

### 4-2. 일상: 문단 몇 개 타깃 치환 (표준 경로)

`hwpx-thesis-editing/SKILL.md`의 6단계를 그대로 따른다. 뼈대만 적으면:

```bash
cp "00. hwpx/<최신본>.hwpx" base.hwpx                                   # 0. 원본 불변
python ~/.claude/skills/hwpx/scripts/map_preflight.py dump base.hwpx > paras.txt   # 1. 현재 텍스트에서 키 확정
# 2. map.json 작성 {"현재 문구": "새 문구"} — 키는 문서 전체에서 유일, 빨간 마커·서식 경계를 가로지르지 않게
python ~/.claude/skills/hwpx/scripts/map_preflight.py check base.hwpx --map map.json   # 3. "전부 매칭"
PYTHONIOENCODING=utf-8 python ~/.claude/skills/hwpx/scripts/fill_hwpx.py replace base.hwpx out.hwpx --map map.json   # 4. exit 0
python tools/hwpx_transfer/verify_replace.py base.hwpx out.hwpx <기대 변경 문단 수>   # 5. PASS
pwsh .claude/skills/hwpx-thesis-editing/scripts/verify-hwpx.ps1 -HwpxPath out.hwpx -PdfPath check.pdf   # 5. Open=True
cp out.hwpx "00. hwpx/YYMMDD_HHMM_논문명.hwpx"                           # 6. 검증 전부 통과 후에만
```

exit code가 0이 아니면 `out.hwpx`는 반쪽짜리다. 즉시 버린다.

### 4-3. 표가 쪽을 넘을 때 (사용자 확정 우선순위)

1. **새 쪽으로 밀어 한 장에 담는다** — `<hp:tbl pageBreak="NONE">`
2. 그래도 넘으면 **컬럼 폭 조정**
3. 그래도 넘으면 **표 나눔** — `pageBreak="TABLE"` + `repeatHeader="1"`

기본값 `pageBreak="CELL"`은 셀 중간을 자르므로 쓰지 않는다. 들어가는지 판정은 `tblplan.py <hwpx>`.

### 4-4. 대형 문서 읽기

본문 XML이 1MB를 넘으면 파이썬 MCP 읽기 도구를 절대 쓰지 않는다. 순서는 rhwp MCP(`hwp_open` → `hwp_doc_search`/`hwp_doc_text` → `hwp_close`) → `map_preflight.py dump` → 직접 `zipfile` + `ElementTree`.

### 4-5. 확인 필요한 자리를 빨간 글자로 만드는 방법

**무엇을 빨갛게 하나.** 접두사 5종(`[DATA PENDING`, `[확정 필요`, `[CITE_TODO`, `[그림 삽입 예정`, `[UNVERIFIED`)으로 시작하는 대괄호 구간을 **여는 대괄호부터 닫는 대괄호까지 통째로**, 본문 문단과 표 셀 양쪽 모두. 참조번호 `[38, 41]`, 신뢰구간 `[0.97, 0.99]`, 양식 라벨 `[양식 1]`은 실제 본문이라 검정을 유지한다. "대괄호 전부 빨강"은 오답이다.

**원리.** hwpx는 글자색을 `header.xml`의 `<hh:charPr>`가 갖는다. 그래서 (1) 본문 charPr를 복제해 `textColor="#FF0000"`만 바꾼 charPr를 header에 추가하고, (2) 문단의 `<hp:run>`을 마커 앞·마커·마커 뒤 세 개로 쪼개 가운데 run의 `charPrIDRef`를 빨간 id로 바꾼다. 텍스트 길이는 그대로라 `linesegarray`는 건드리지 않아도 된다.

**경로 1 — 조립 때 자동(권장).** `blocks_to_hwpx.py`가 이 일을 한다. `GUIDE_MARKER_RE`가 마커를 찾고, `marker_aware_runs()`가 run을 쪼개며, `red_char_pr_id()`가 빨간 charPr를 header에 없으면 만든다. MD에는 색 정보를 두지 않는다. 재조립해도 색이 자동으로 따라오게 하려는 것이다.

**경로 2 — 이미 있는 hwpx에 사후 적용.** 전체 재조립을 못 쓰는 운영 단계라면 `blocks_to_hwpx.py`의 위 두 함수를 가져다 section XML에 직접 돌린다. 순서: 최신본 복사 → header에 빨간 charPr 추가 → 섹션별로 마커 run 분리 → ZIP 재포장(엔트리 순서·압축 방식 유지) → 아래 검증 → `verify-hwpx.ps1`로 `Open=True` 확인 → 한글에서 재저장. **재저장하면 charPr id가 바뀌므로** 이후 검증은 id를 외우지 말고 header의 `#FF0000`에서 다시 끌어온다.

**검증 스크립트.** 마커가 전부 빨간 run 안에 있는지 센다. 표를 감싼 바깥 run이 셀 텍스트까지 끌어안으므로 `run.iter()`가 아니라 **직접 자식 `<hp:t>`만** 세야 한다(이걸 놓치면 멀쩡한 파일이 "검정 500건"으로 나온다. 실제로 겪었다).

```python
import zipfile; from xml.etree import ElementTree as ET
HH='{http://www.hancom.co.kr/hwpml/2011/head}'; HP='{http://www.hancom.co.kr/hwpml/2011/paragraph}'
z=zipfile.ZipFile('out.hwpx'); hdr=ET.fromstring(z.read('Contents/header.xml'))
red={c.get('id') for c in hdr.iter(HH+'charPr') if any(e.get('textColor')=='#FF0000' for e in c.iter())}
M=['[DATA PENDING','[확정 필요','[CITE_TODO','[그림 삽입 예정','[UNVERIFIED']; ok=bad=0
for n in [x for x in z.namelist() if x.startswith('Contents/section')]:
    for run in ET.fromstring(z.read(n)).iter(HP+'run'):
        t=''.join(e.text or '' for e in run.findall(HP+'t'))   # 직접 자식만
        k=sum(t.count(m) for m in M)
        if run.get('charPrIDRef') in red: ok+=k
        else: bad+=k
print('빨강', ok, '검정', bad)   # 검정 0 이어야 완료
```

타깃 치환 뒤에는 `verify_replace.py`의 검증 8이 같은 것을 base와 대조한다. 치환 키가 마커 경계를 가로지르면 마커 앞부분이 검정이 되는데 다른 검증은 전부 통과하므로, 이 숫자가 유일한 방어선이다.

### 4-6. 표가 쪽을 넘을 때 실제로 고치는 방법

**원리.** `<hp:tbl>`의 `pageBreak` 속성이 표의 쪽 넘김 방식이다. `CELL`(기본값)은 셀 중간을 자르고, `NONE`은 표를 나누지 않고 통째로 다음 쪽으로 밀며, `TABLE`은 행 경계에서 나눈다. 우선순위는 4-3과 같다: NONE → 열폭 조정 → TABLE+`repeatHeader="1"`.

**경로 1 — 조립 때.** `style_map.json`의 표 스타일에 `"pageBreak": "NONE"`을 두면 `blocks_to_hwpx.py`가 모든 본문 표에 적용한다. 학교 양식은 대개 `CELL`이므로 양식에서 실측한 값을 그대로 두면 안 된다. 이 값 하나가 회귀하면 표 수십 개가 한꺼번에 셀 단위로 쪼개진다(2026-09-12에 회귀 차단 작업을 따로 했다).

**경로 2 — 이미 있는 hwpx.** 속성만 바꾸므로 텍스트 길이가 안 변해 `linesegarray` 걱정이 없다. 본문 섹션에서 일괄 치환한다.

```python
import zipfile, shutil
src, dst = 'base.hwpx', 'out.hwpx'
with zipfile.ZipFile(src) as zi, zipfile.ZipFile(dst, 'w') as zo:
    for info in zi.infolist():                       # 엔트리 순서·압축 방식 유지
        data = zi.read(info.filename)
        if info.filename == 'Contents/section2.xml':  # 본문 섹션만. 전면부 제목 상자는 두 줄짜리라 그대로 둔다
            data = data.replace(b'pageBreak="CELL"', b'pageBreak="NONE"')
        zo.writestr(info, data)
```

`pageBreak="CELL"`은 `<hp:tbl>`에만 있는 속성이므로(문단 `<hp:p>`는 `pageBreak="0|1"`) 전역 치환해도 안전하다. 그래도 치환 전후 개수를 세어 확인한다.

**판정과 확인.**

```bash
python tools/hwpx_transfer/tblplan.py out.hwpx        # 표마다 fits / pageBreak / 권고. not-fits 0, CELL 0 이어야 한다
pwsh .claude/skills/hwpx-thesis-editing/scripts/verify-hwpx.ps1 -HwpxPath out.hwpx -PdfPath check.pdf
powershell.exe -NoProfile -File .claude/skills/hwpx-thesis-editing/scripts/render-pdf.ps1 -PdfPath check.pdf -OutDir png -Pages "표가 있는 쪽"
```

`tblplan.py`는 XML에 **선언된** 행 높이(최소값) 기준이라 셀 내용이 길어 실제로 자란 표는 잡지 못한다. 마지막은 반드시 PDF를 PNG로 렌더해 눈으로 본다. `not-fits`로 나온 표는 2단계(열폭)로 가고, 그래도 안 되면 그 표만 `pageBreak="TABLE" repeatHeader="1"`로 바꾼다. 셀 폭을 만질 때는 열 그리드(`colAddr`/`colSpan`)와 합이 맞아야 한다. 안 맞으면 한글이 행을 재배치해 행 전체가 깨진다.
